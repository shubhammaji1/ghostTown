# 2. PRODUCT VISION

Build GhostTown as a developer tool that allows programmers to simulate realistic user journeys without manually writing every browser test.

## Example workflow

A developer is working on a React application.

Their application runs at:

http://localhost:3000

Inside VS Code, they open GhostTown.

They see:

**Project:** Current React Workspace

**Target:** localhost:3000

**Testing Mode:** Hybrid

**Synthetic Users:** 5

They select:

- First-Time Visitor
- Impatient User
- Mobile User
- Keyboard-Only User
- Curious Explorer

Then click:

**Run Population Test**

GhostTown launches controlled, isolated browser sessions.

Each persona attempts tasks such as:

- Opening the homepage
- Navigating between pages
- Completing forms
- Searching for information
- Finding and activating buttons
- Testing validation
- Following defined user objectives
- Checking relevant accessibility behavior

The extension reports actual observations.

Example:

**Issue #1: Submit button does not complete the expected action**

Persona: First-Time Visitor

Page: /register

Observed: The button receives a click, but the expected confirmation does not appear.

Evidence:
- Failed assertion
- Browser screenshot
- Action timeline
- Playwright trace

Reproduction:
1. Open /register.
2. Enter valid synthetic user information.
3. Select Submit.
4. Observe that the required success condition is not satisfied.

GhostTown must not classify an unchanged page as a definite bug without an expected outcome or corroborating evidence.

The developer can inspect the issue and optionally navigate to a source location when reliable source mapping exists.

# 3. PRODUCT POSITIONING

GhostTown is not:

- Another chatbot extension
- A replacement for Playwright
- A generic load-testing tool
- A real-human behavior prediction engine
- A tool for manufacturing website traffic
- A website screenshot generator
- An AI wrapper without deterministic verification

GhostTown is:

**A developer-focused synthetic user testing environment that combines persona-driven exploration, deterministic browser automation, runtime evidence, and intelligent issue investigation.**

## Key product differentiators

### A. Developer-native experience

Everything necessary for local test execution is available inside VS Code.

### B. Persona-driven exploration

Different testing profiles can trigger different navigation approaches, environments, retry budgets, and accessibility checks.

### C. Real execution

Every reported browser interaction corresponds to an actual action.

### D. Evidence-backed defects

Every confirmed defect includes observable proof.

### E. Local-first privacy

Developers can use deterministic testing without sending source code or browser content to an external service.

### F. Independent testing engine

The core can later support CLI, CI/CD, GitHub Actions, and hosted execution.

Support VS Code Restricted Mode safely.

- Allow viewing existing safe configuration where appropriate.
- Disable browser execution initiated from untrusted workspace configuration.
- Disable automatic project scripts.
- Disable executable project hooks.
- Do not start workspace processes.
- Show an informative explanation.

Recheck trust at the point of execution, not only when displaying buttons.

- VS Code desktop on Windows

- VS Code desktop on Linux

For the MVP, do not promise native browser execution inside vscode.dev.

Detect unsupported web extension hosts and provide a truthful unsupported-environment message.

For Remote SSH, WSL, and Dev Containers, identify whether the extension host and target application run locally or remotely.

Do not silently execute against the wrong machine.

Provide documented remote-host limitations and configuration.

# 13. TESTING MODES

Implement three execution modes.

## Mode 1 — Deterministic Testing

Runs defined scenarios with Playwright.

No AI required.

Suitable for:

- Registration
- Login
- Search
- Navigation
- Checkout sandbox
- Form validation
- Basic accessibility checks

## Mode 2 — AI-Assisted Exploration

Uses a configured LLM to choose bounded browser actions based on a persona and allowed objective.

The agent may:

- Inspect the current page
- Identify available controls
- Choose an allowed action
- Observe results
- Continue or stop

All actions must pass through the policy engine.

## Mode 3 — Hybrid Testing

Combines deterministic workflows with AI-assisted exploration.

Example:

A deterministic script opens the product page.

An AI persona explores visible product controls.

A deterministic assertion verifies an expected outcome.

## Important

The user must be able to select a mode explicitly.

If AI credentials are missing, deterministic testing must still work.

Never silently invent AI decisions.

# 14. REAL PLAYWRIGHT BROWSER ENGINE

This is the product's most important component.

Implement the actual browser executor before sophisticated visual dashboards.

## Execution lifecycle

1. Validate configuration.
2. Verify target and execution policy.
3. Allocate a runner slot.
4. Start the browser.
5. Create a fresh browser context.
6. Apply persona settings.
7. Open the target page.
8. Execute actions.
9. Evaluate assertions.
10. Capture evidence.
11. Persist results.
12. Close the context.
13. Release resources.

## Supported browser actions

- Navigate
- Click
- Fill
- Select
- Check/uncheck
- Scroll
- Press keyboard keys
- Wait for locator
- Inspect accessible controls
- Capture screenshot
- Assert visible
- Assert URL
- Assert text
- Assert response
- Finish

## Isolation

Use separate browser contexts for distinct synthetic users.

Clear:

- Cookies
- Session storage
- Local storage
- Permissions
- Session credentials

between independent runs unless an explicit scenario requires persisted state.

Browser contexts isolate session state but are not a secure sandbox against arbitrary hostile websites.

For untrusted remote targets, require stronger process/network isolation or explicitly restrict the execution mode.

## Browser installation

Do not assume Chromium is installed.

Provide an environment check.

If the required Playwright browser is missing:

- Explain the missing dependency.
- Offer an explicit Install Browser action.
- Run the supported browser installation workflow with consent.
- Display progress and errors.
- Recheck compatibility afterward.

Do not silently download large browser binaries when the extension activates.

Bundle the compatible Playwright library correctly.

Do not rely on undeclared globally installed packages.

## Execution limits

Enforce:

- Maximum browser sessions
- Maximum pages
- Maximum steps
- Maximum duration
- Maximum AI decisions
- Maximum retries
- Maximum screenshots
- Maximum artifact size
- Maximum navigations
- Rate limits

Provide a Stop button that reliably cancels active work.

# 15. LOCAL RUNNER ARCHITECTURE

Never run heavy browser workloads synchronously on the VS Code extension host.

Create a dedicated runner package/process.

## Architecture

Extension Host
→ Runner Controller
→ Managed Child Process
→ ghosttown-core
→ Playwright Browser
→ Test Events
→ VS Code UI

## IPC

Use a versioned, typed JSON message protocol over local process standard input/output or another explicitly secured local channel.

Example event categories:

- runner.ready
- run.started
- session.started
- action.started
- action.completed
- assertion.failed
- issue.detected
- artifact.created
- session.completed
- run.completed
- run.cancelled
- runner.error

Every message must include:

- Protocol version
- Run ID
- Event type
- Sequence number
- Timestamp
- Validated payload

Validate incoming events before rendering.

## Process management

Use controlled process spawning without shell execution.

Requirements:

- Explicit executable
- Explicit argument array
- Restricted environment variables
- Graceful cancellation
- Termination escalation after timeout
- Child-process cleanup
- Browser-process cleanup
- Crash detection
- Structured error reporting

Do not allow the webview to launch arbitrary processes.

## Event streaming

Stream actual progress to the extension.

Use bounded event buffers and backpressure handling.

Avoid flooding the webview with every internal low-level browser event.

Persist results before relying on them for the dashboard.

# 25. SECURITY MODEL

Security is mandatory.

## Local execution

GhostTown tests applications on a developer-controlled machine or remote extension host.

Require explicit user action to execute tests.

Do not silently browse arbitrary URLs.

## URL policies

Enforce:

- Allowed origins
- Allowed protocols
- Redirect rules
- Navigation limits
- Explicit external-domain approval

Localhost testing is permitted under a user-selected local development profile.

For remote untrusted targets, enforce stronger network isolation or refuse unsafe execution.

Application-level checks alone do not provide full isolation from malicious websites.

## Workspace safety

- Respect Workspace Trust.
- Never execute arbitrary commands from untrusted configuration.
- Never follow AI-generated shell instructions.
- Never run project scripts automatically.
- Do not execute files discovered during scanning.

## Webview security

- Strict Content Security Policy
- Nonced scripts where appropriate
- Restricted localResourceRoots
- No unsafe inline script execution
- Validate every webview message
- Escape untrusted content
- Avoid unsafe HTML injection
- No direct filesystem access from webview code
- Only allowlisted extension commands

## Data security

- API keys in SecretStorage
- Sensitive browser artifacts restricted
- Safe path handling
- No directory traversal
- No secret logging
- Clear local-data deletion behavior

## AI safety

No model should be allowed to override:

- Target restrictions
- Allowed actions
- Budget limits
- Workspace permissions
- Artifact privacy policy

# 26. PERFORMANCE REQUIREMENTS

The extension must remain responsive while tests run.

## Goals

- Fast activation
- Minimal idle CPU usage
- No browser launch on startup
- No unnecessary repository scanning
- Smooth sidebar interactions
- Bounded event updates
- Efficient history loading
- Reliable worker cleanup

## Browser concurrency

Default to one or two simultaneous browser sessions.

Allow users to increase concurrency subject to safe limits.

Do not attempt to launch dozens of browsers on low-resource machines without checking capacity.

## Memory management

- Close browser contexts.
- Terminate worker processes.
- Dispose event listeners.
- Release screenshots and trace handles.
- Clean temporary files.
- Avoid retaining complete DOM snapshots in memory indefinitely.

Provide graceful degradation when resources are limited.
